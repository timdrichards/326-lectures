Status codes: whose problem?

The first digit tells you. The server sends every one.

1xxInformationalHold on, still working.rare; you will not send one
2xxSuccessIt worked.200 OK, 201 Created, 204
3xxRedirectionLook somewhere else.301 Moved, 304 Not Modified
4xxClient errorBad request. Fix the request.400, 401, 403, 404
5xxServer errorThe server broke. Fix the server.500, 503

4xx: the server is saying the request was the problem. 5xx: the server is saying it was.

201 and 200: same body

Only the first line differs. That line is what a program reads.


$ curl -i -X POST localhost:3000/entries ...
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8

{"title":"From curl","body":"Hello"}

# the same route, with res.status(201) removed:
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"title":"From curl","body":"Hello"}

A 400: the client caused it

The request left out a field. The server checked, and said so.


$ curl -i -X POST localhost:3000/entries \
    -H "Content-Type: application/json" \
    -d '{"title":"Groceries"}'
HTTP/1.1 400 Bad Request
Content-Type: application/json; charset=utf-8

{"error":"title and body are required"}

# the server's terminal: nothing at all.

Send "body":"Milk" too and the same request gets 201 Created. Nothing on the server changed.

What a 500 looks like

The status says whose side. The terminal says what.


$ curl -i -X POST localhost:3000/entries ...
HTTP/1.1 500 Internal Server Error

# and in the server's own terminal:
TypeError: Cannot destructure property 'title'
  of 'req.body' as it is undefined.

Why a header, and not the JSON?

The body is the thing you asked for. Headers are facts about it.

A cheap way to pass information back. The browser can read a header without downloading and parsing the body, and can even ask for the headers alone.

Details about the content being returned. Content-Type says what the body is, so the reader knows how to handle it before reading a byte of it.

It works for any body. /entries sends HTML, where a count field has nowhere sensible to go. And a JSON list can stay a list.

A total inside the JSON is also a common, reasonable design. It is a choice, not a rule.

Example: Content-Type

One server, three kinds of body.


$ curl -I localhost:3000/entries
Content-Type: text/html; charset=utf-8

$ curl -I localhost:3000/style.css
Content-Type: text/css; charset=UTF-8

$ curl -i -X POST localhost:3000/entries ...
Content-Type: application/json; charset=utf-8

The browser reads this before the body. text/html it draws as a page, text/css it applies as a style sheet, and application/json is data for code to read. Label a page text/plain and the browser shows the raw tags instead.

HEAD: ask for the headers only


$ curl -I localhost:3000/entries
HTTP/1.1 200 OK
X-Total-Count: 3
Content-Type: text/html; charset=utf-8
Content-Length: 491
ETag: W/"1eb-1vdI0qIW1zTgUvgUSf1PuZYyfbI"

curl -I sends a HEAD request. It is GET without the body: the same status and headers, zero bytes of page. Express answers HEAD for every GET route automatically.

In an app, HEAD is how a program asks about something without downloading it: does this page still exist, how big is this file, has it changed since I last saw it, how many entries are there.

TCP, HTTP, and your app

Three layers. Each one rides on the one below it.

HTTPS: the same text, encrypted


$ curl -v https://www.umass.edu/
* Connected to www.umass.edu (104.18.21.94) port 443
* SSL connection using TLSv1.3 / ...

HTTPS is HTTP sent through an encryption layer called TLS. The request and response inside are exactly the text you saw today.

Anyone between you and the server, on café Wi-Fi or at your provider, sees scrambled bytes, not your password or your page. Only the two ends can read it.

The certificate is how your browser checks it is talking to the real umass.edu and not an impostor.

A status code is a promise

Nothing stops a server from saying 200 when it failed.


res.status(200).json({ error: 'No such entry' });


$ curl --fail localhost:3000/lie/9
{"error":"No such entry"}

$ curl --fail localhost:3000/honest/9
curl: (22) The requested URL returned error: 404

--fail tells curl to treat any 4xx or 5xx as a failure. The 200 route sails through as a success, error message and all. Every client reads the number first, so a server that answers 200 when it failed is lying to every program that trusts it.

A method is a promise too

GET promises it only reads. Programs act on that promise.


// looks harmless, breaks the promise
app.get('/entries/:id/delete', (req, res) => {
  entries.splice(req.params.id, 1);
  res.redirect('/entries');
});

Browsers that preload links, and search engines crawling a site, follow every GET link they find, because GET promises to change nothing.

Put a delete behind a GET link and a crawler can empty your data without anyone clicking. That is why deleting uses DELETE.

Commit this to memory (1 of 2)

Keep all of it conceptually. These details are worth knowing cold.

An HTTP message is plain text in a fixed order: a start line, headers, a blank line, then an optional body.

A request starts with the method, path and version. A response starts with the version, a status code, and a phrase for people.

The first digit of a status says what happened: 2xx it worked, 3xx look elsewhere, 4xx the request was wrong, 5xx the server failed.

Know six by heart: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 500 Internal Server Error.

Commit this to memory (2 of 2)

GET only reads, so it is safe to repeat. PUT and DELETE change things but are still safe to repeat. POST is neither.

Safe to repeat matters because networks drop responses and clients retry. A retried POST can do the thing twice.

Headers are named pieces of text about the message. Content-Type tells the reader how to parse the body.

Express writes all of this for you: res.status() sets the code, res.set() adds a header, and res.json() sets Content-Type and sends the body. curl -i shows you what it actually sent.

Activity: Deleting Twice

Send the same DELETE twice to your own server, first to /entries/0 and then, after a restart, to /entries/2. Use curl -i and the X-Total-Count header to see what each request returned and what it did to the entries.

Decide together: the first DELETE /entries/2 succeeds with 204. Should the identical second one return 404, because nothing is there any more, or 204, because what the client asked for is true either way?

  • 404 or 204 for a repeated delete: what did the room decide, and what would a client that retries actually need?
  • A client sends malformed JSON and gets a 400. The client caused it, so what is the server's job?

Bad JSON: the right 400

The client caused it. Here is what our server sends back.


$ curl -i -X POST localhost:3000/entries \
    -H "Content-Type: application/json" \
    -d '{title:"Groceries"}'
HTTP/1.1 400 Bad Request
Content-Type: text/html; charset=utf-8

<pre>SyntaxError: Expected property name ...
 at parse (.../body-parser/lib/types/json.js:96:19)

Right status, wrong body: HTML, with our stack trace and file paths. The same trace fills our terminal.

The fix: an error handler


// after every route, before app.listen
app.use((err, req, res, next) => {
  if (err.type === 'entity.parse.failed') {
    res.status(400).json({ error: 'invalid JSON' });
    return;
  }
  next(err);
});


HTTP/1.1 400 Bad Request
Content-Type: application/json; charset=utf-8
{"error":"invalid JSON"}

Still a 400. Now the client can read it, nothing leaks, and the terminal stays quiet.
