First: where you are

Your lab work lives in one repository: the web-server folder in your gantry workspace. Unit work and anything you try out goes elsewhere in the workspace, not in here.

git rev-parse --show-toplevel

That command answers one question: which repository am I standing in? It walks up from wherever you are until it finds the .git directory and prints the folder holding it, so it tells you where the repository actually starts, not just where your terminal is.

It must end in /web-server. Your gantry workspace means the repository starts too high; "not a git repository" means you are outside one. Fix either before starting, steps in Canvas under Lab 01.

Ten seconds, out loud, every week. Do not skip it because it feels repetitive to you; it is not repetitive to the student who has been quietly wrong since Lab 01. Have them actually run it rather than nod. The two wrong outputs are the gantry workspace path, which means the repo is rooted too high, and "not a git repository", which means they are standing outside it. Why it matters, if anyone asks: the autograder clones their repo and reads server.js from the top of it. A repo rooted one level too high does not fail loudly, it just scores about 40 on a lab that was actually finished.

What This Lab Is About

You already have an Express server that runs. Today you put it under version control and get it onto GitHub properly: ignore what should not be tracked, make one real commit, and push it to a repository of your own.

This is the same sequence every sprint and the whole team project runs through. Nothing about it gets more complicated later. There is just more of it.

The commands are on the next few slides, and the full write-up is in Canvas under Lab 01. Use whichever you prefer.

This slide is the whole explanation. Do not walk the steps from the front; they are written properly in Canvas and reading them aloud just delays people starting. WHAT THE HOUR ACTUALLY IS, for you rather than the room: write a .gitignore, git init, one commit, then gh repo create with --source=. --remote=origin --push, then confirm and submit github.json to Gradescope. Fifteen minutes of typing for someone whose environment works. Budget the rest for the environment and for people who have not started. THE FOUR THINGS THAT ACTUALLY GO WRONG, in the order you will meet them: 1. COMMITTING node_modules. By far the most common. Thousands of files, a very slow push, and unpicking it is a hard git exercise that is not what today is about. The fastest fix is to delete the .git directory and start the lab again; say that plainly rather than teaching git rm --cached to someone on their first day of version control. The cause is nearly always a .gitignore written after git init, saved in the parent folder, or saved as gitignore.txt by an editor. 2. SKIPPING git status. It is the checkpoint that catches the above before it becomes a commit. Make people actually run it and read the output. 3. NO GIT IDENTITY. If git refuses with a message about identity, they never set user.name and user.email. That is on the Installing Git page, and it matters beyond today: commits stamped with an address GitHub does not recognise do not count as their work when sprints are graded. 4. gh NOT AUTHENTICATED. gh auth status first if you suspect it, then gh auth login and follow the browser prompts. Anyone working outside the container may not have the GitHub CLI at all; creating the repo in the browser and pushing with git remote add plus git push is completely fine today.

How You Submit

  1. Make github.json in your project folder, with your repository URL inside it.
  2. Upload that one file to Gradescope, through the Lab 1 link in Canvas.
Pushing to GitHub is not submitting. The code on GitHub is the work. The upload to Gradescope is what records it.

github.json is in your .gitignore on purpose: it is your submission artifact, not part of the project, so it never gets committed. The lab is due tonight at 11:59 PM.

Say this one out loud. Do not just advance past it. Every term people do all of the work and lose the credit at the last step, and the reason it keeps happening is that it does not feel like a step: once GitHub shows the code, the lab feels finished. Two things students get wrong here: - They try to commit github.json, or they are confused that it is in the .gitignore. It is deliberately ignored. It holds the repo URL and exists only to be uploaded; it is not part of the project. - They put the repository NAME in it rather than the full URL. The autograder reads the URL and clones it, so a bare name fails with nothing obviously wrong on their side. Before anyone leaves, actually ask whether they submitted, rather than whether they finished. Gradescope shows a submission timestamp; that is the thing to confirm. If Gradescope will not accept it, do not let them leave planning to sort it out later. Have them message Tim through the Canvas Inbox while they are still in the room.
