First: where you are

Your lab work lives in one repository: the web-server folder in your gantry workspace. Unit work and anything you try out goes elsewhere in the workspace, not in here.

git rev-parse --show-toplevel

That command answers one question: which repository am I standing in? It walks up from wherever you are until it finds the .git directory and prints the folder holding it, so it tells you where the repository actually starts, not just where your terminal is.

It must end in /web-server. Your gantry workspace means the repository starts too high; "not a git repository" means you are outside one. Fix either before starting, steps in Canvas under Lab 01.

Ten seconds, out loud, every week. Do not skip it because it feels repetitive to you; it is not repetitive to the student who has been quietly wrong since Lab 01. Have them actually run it rather than nod. The two wrong outputs are the gantry workspace path, which means the repo is rooted too high, and "not a git repository", which means they are standing outside it. Why it matters, if anyone asks: the autograder clones their repo and reads server.js from the top of it. A repo rooted one level too high does not fail loudly, it just scores about 40 on a lab that was actually finished.

What This Lab Is About

You have a repository with your Express server in it. Today you add an About page on a branch rather than straight onto main, open a pull request proposing the change, and merge it.

A pull request is how a change gets proposed and looked at before it reaches main, so the branch everyone works from stays working.

This is the exact workflow every sprint contribution uses. Doing it alone on a small change now means the first time it matters is not the first time you have seen it.

The commands are on the next few slides, and the full write-up is in Canvas under Lab 02. Use whichever you prefer.

Keep this short, ninety seconds. The deck carries the steps this week, so the room can start as soon as they understand the shape. The Loop You Will Use All Term

1
branch
2
commit
3
push
↻ repeat as often as needed
4
pull request
5
merge

A branch is a private line of work: commits on it do not touch main, so if it turns out wrong you delete it and nothing is lost. A pull request is the proposal to merge it, and it shows exactly which lines would change.

One commit is one change you could describe in a sentence. Adding the route is a commit. Adding the view is a commit. A whole afternoon is not. Commit when something works, push when you want it somewhere other than your laptop, and expect to go round that pair several times before the branch is ready.

Thirty seconds on this. Say the loop out loud once, and say that every sprint runs through exactly it. The line worth adding, because it is the one that makes branching feel worth the trouble rather than like extra ceremony: on a team, four people can be on four branches at once and none of them break each other's work. Alone today that benefit is invisible, which is exactly why the habit has to be built before the project starts.

Before You Start

1. git status says nothing to commit, working tree clean.

2. git branch shows * main.

3. Your repository is public, or the autograder cannot clone it.

4. gh is logged in. If not: gh auth login.


gh repo view --json isPrivate --jq .isPrivate
# prints false. if true:
gh repo edit --visibility public --yes
gh auth status

All of this can be done in the GitHub web interface instead, and that is a real way to work. Do it at the command line anyway: that is the version that transfers to a server, to a script, and to every tool with no buttons.

Run these as a room before anyone starts, it takes a minute and it saves the hour. THE PRIVATE REPO IS THE ONE THAT MATTERS. It is silent: the lab works perfectly, the merge succeeds, and the autograder simply cannot clone it. gh repo edit --visibility public --yes fixes it. gh auth status catches the other silent one. An unauthenticated gh does not fail until gh pr create, five steps later, where the error reads as a problem with the pull request. A dirty working tree from last week is fine and does not need solving now; they can commit it to main first, or stash it.

1. Branch first, then build

Branch before you change anything, so every commit lands on it rather than on main. A branch is a place to be wrong safely: main keeps working while you experiment, and a bad idea is deleted rather than unpicked. On a team it is also what lets four people build four things at once.


git checkout -b feature/about-page
git branch


npm install ejs

git branch should now show the asterisk next to feature/about-page.

The order is the whole point and it is the most common thing to get backwards. Someone who edits first and branches later has their work on main already, which is recoverable but is not what today is teaching. If someone has already committed to main by mistake, the quickest honest fix in the room is: git checkout -b feature/about-page, then on main git reset --hard origin/main. Do that WITH them rather than telling them the command.

2. Tell Express to render views

Two lines in server.js. The first goes just after const app = express(), the second alongside your other routes, before app.listen.


app.set("view engine", "ejs");


app.get("/about", (req, res) => {
  res.render("about", { title: "About" });
});

res.render looks for views/about.ejs. That file does not exist yet, so the route will error until the next step.

Two failures land here and they look the same from the browser. 1. FORGETTING app.set. Express then has no view engine and res.render fails. The error names the module, not the missing setting, so it reads as an install problem. 2. THE FILE IN THE WRONG PLACE. views/ must be at the top of the repository, beside server.js. A views folder one level up, or nested, gives 'Failed to lookup view'. Both are worth catching by asking them to read the error out loud rather than by reading their screen for them.

3. Create views/about.ejs

Plain HTML. It is a template, so it can hold EJS later.


<!doctype html>
<html lang="en">
  <head><title>About</title></head>
  <body>
    <h1>About</h1>
    <p>What this project is.</p>
  </body>
</html>

Restart with node server.js and open localhost:3000/about before you commit.

Make them actually load the page. A commit of a broken route is a worse outcome than being five minutes behind, and the restart is the step people skip: the server was already running, so nothing looks wrong. Restarting is not optional here even though the route was added a step ago. Node has the old file in memory.

4. Commit and push the branch

Four files changed: the server, the new view, and the two package files npm install touched.


git add server.js views/about.ejs
git add package.json package-lock.json
git commit -m "add About page"


git push -u origin feature/about-page

-u links this branch to the remote one, so later pushes on it are just git push.

git status before git add, every time. It is the checkpoint that catches node_modules before it becomes a commit, which is still the most expensive mistake available in this lab. If the push is rejected asking them to set an upstream, they dropped the -u. If it asks for a username and password, gh is not authenticated and git is falling back to HTTPS basic auth, which GitHub no longer accepts.

5. Open the pull request

A pull request says here is a change, have a look before it goes in. It shows the exact lines that would change, gives your teammates somewhere to comment and approve, and leaves a permanent record of what was changed and why. That record is the reason it is still worth opening one when you are working alone. This command opens the GitHub form in your browser; fill in the title and body before you submit it.


gh pr create --web

Prefer the terminal? gh pr create with no flags prompts you for the same fields.

If the browser does not open, they are almost certainly in the container without a browser handoff. gh pr create with no flags works entirely in the terminal and is a completely fine substitute; so is opening the repo on github.com and using the Compare and pull request button that appears after a push.

Writing the Pull Request

Title: short and specific. Add About page, not Updates.

The body answers three questions for whoever reads it next, which may be a teammate, or you three months from now:

What changed? The files, and what you did to them. “Added a GET /about route in server.js and created views/about.ejs.”

Why? What it is for. “Gives visitors a page explaining what the application is.”

How do I check it? What the reviewer should run. “Start the server and open localhost:3000/about.”

Nothing checks this and it is still the point. A pull request with an empty body is the thing your teammates will not review.

Spend a real two minutes here. It is the only part of the lab that is not mechanical, the autograder cannot see it, and it is what the sprint rubrics grade later under README and PR Workflow. The framing that lands: the body is not paperwork, it is what makes the difference between a teammate approving in two minutes and leaving it for a day. If someone has written one line, ask them the third question out loud. Almost nobody includes how to verify, and it is the one a reviewer actually needs.

How You Submit

  1. Check the diff first: gh pr view --web, Files changed. Four files, no more.
  2. Merge it: gh pr merge --merge --delete-branch
  3. Upload github.json to Gradescope, through the Lab 2 link in Canvas.
Pushing to GitHub is not submitting. The code on GitHub is the work. The upload to Gradescope is what records it.

Same github.json as Lab 1, the URL has not changed. The merge command also deletes the branch, puts you back on main and pulls the merged commit, so git log --oneline should show your About page commit on main. The lab is due tonight at 11:59 PM.

Two separate things get lost on this slide, so do not advance past it quickly. 1. THE DIFF CHECK. If Files changed shows anything beyond server.js, views/about.ejs, package.json and package-lock.json, they staged something they did not mean to, and node_modules is the usual culprit. Better to find it here than after the merge. 2. THE GRADESCOPE UPLOAD. Same as last week and it will happen again: merging feels like finishing, because on GitHub it is. Nothing is recorded until github.json is uploaded. Ask people whether they SUBMITTED, not whether they finished. The Gradescope timestamp is the thing to see. A merge that refuses because the branch is out of date is not a problem today, nobody else is pushing to their repo; if it happens it usually means they committed to main separately at some point.
